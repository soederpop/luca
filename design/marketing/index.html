import container from 'luca'

const operator = container.feature('assistant', {
  systemPrompt: `You operate the staging API.
    Search the runbooks first. Inspect the service and delegate
    a patch with coder.run() through evalCode.
    Verify the result before reporting back.`,
})

operator.use(container.feature('contentDb', {
  rootPath: './brain',
}))
operator.use(container.feature('secureShell', {
  host: 'staging-api',
}))
container.addContext('coder', container.feature('claudeCode', {
  cwd: container.paths.resolve('services/api'),
}))
operator.use(container.feature('vm'))

await operator.start()
await operator.ask(
  'Investigate the failing health check on staging-api.'
)

The assistant is
part of the application.

Your API, background service, command-line toolkit, and assistant are built from the same runtime. They share capabilities, observable state, and events. The assistant can discover and operate the application it lives in.

Shape that runtime into a task-specific, environment-specific harness. Choose its model, connect its Markdown brain, attach tools, and define its instructions and hooks. The application architecture is also the agent architecture.

A full Markdown brain.
Built to be searched.

Contentbase turns Markdown into a structured knowledge system. Runbooks, architecture decisions, project knowledge, and task records stay readable as files and become queryable context for the assistant.

Knowledge with structure

Define content models, parse frontmatter, query records, and validate documents. Your application and its assistants work with the same collection.

Search by meaning

Find related knowledge with vector search, match exact terms with BM25, or combine both with hybrid search.

Context the agent can navigate

Attach the collection with assistant.use(brain). The assistant inherits tools to explore models, query documents, search semantically, and read the sections it needs.

brain.ts / Contentbase integration
import container from 'luca'

const brain = container.feature('contentDb', {
  rootPath: './brain',
})
await brain.load()

// The application can search the same knowledge.
const related = await brain.hybridSearch(
  'How do we recover from a failed deployment?',
  { limit: 5 },
)

// The assistant gets navigation and search tools.
const operator = container.feature('assistant', {
  systemPrompt: 'Use our runbooks to investigate incidents.',
})
operator.use(brain)
operator.use(container.feature('vm'))
await operator.start()
await operator.ask(
  'Find the rollback procedure and its preconditions.'
)
Requires a Markdown collection and configured model / embedding access. The assistant’s semantic search tool can fall back to text search.

The agent can write code.
Inside its own runtime.

Attach the VM and the assistant gets live evaluation with the whole container in scope. It can compose capabilities in code, inspect running helpers, and act on the state already in memory.

evalCode / TypeScriptSame process
// Available to the assistant after assistant.use(vm).
const ssh = container.feature('secureShell')
ssh.useHost('staging-api')

const diagnostics = await ssh.exec(
  'journalctl -u api -n 80 --no-pager'
)

// Hand the real diagnostic output to a coding agent.
const coder = container.feature('openaiCodex', {
  cwd: container.paths.resolve('services/api'),
})
const session = await coder.run(
  `Investigate this service failure: ${diagnostics}`
)
session.result

A tool call can become a program.

Combine SSH, coding sessions, filesystem operations, and your own features in one evaluation. Use loops, conditions, and asynchronous code when the task demands it.

container is the live application. assistant is the consuming agent. Results and console output come back through the tool call.

This is live execution with real side effects. The environment you provide defines what the harness can reach.

The VM runs in the current process. It is not a security sandbox or a separate CLI session.
